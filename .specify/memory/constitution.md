# ClassroomQuiz Constitution

## Core Principles

### I. 核心需求優先

- 必須完成老師指定的全部核心功能，包含老師端、學生端、Guided Notes 匯入匯出、
  搶答順位與活動階段同步。
- 不得加入題組匯入、CSV 搶答紀錄匯出、積分、排行榜、AI 答案驗證等額外功能。
- SpecKit 組與 OpenSpec 組的功能必須一致。
- 任何影響使用者功能與操作流程的變更，都必須先與另一組討論並記錄結論，
  再依確認結果修訂規格及後續產物，不得先行實作。

理由：以課程要求及兩組功能一致性作為範圍基準，防止未確認的功能擴張。

### II. 規格驅動開發

- 必須依序遵守 Constitution → Specify → Plan → Tasks → Implement 流程。
- 需求規格必須明確、可測試，並提供可判定通過或失敗的驗收條件。
- 規格、設計圖、程式碼與 Demo 必須一致；發現差異時，必須修正並重新驗證。
- 不得在需求尚未確認時自行加入功能。
- 所有 AI 產出的文件都必須接受人工審查；未審查文件不得視為已確認基準。

理由：以可審查、可追溯的規格約束 AI Agent 開發，確保成果符合已確認的需求。

### III. PlantUML 設計優先（Design-First with PlantUML）

本原則為課程指定的 Diagram First Development 強制規則，不得省略。

規格制定階段（Specification Phase）：

- 在 `speckit.specify` 階段，必須使用 PlantUML 語法生成以下三種圖表：
  1. Component Diagram：描述系統架構與組件。
  2. Class Diagram：描述類別及組件。
  3. Sequence Diagram：描述系統時序互動。
- 所有 `.puml` 檔案必須儲存在專案根目錄的 `./diagrams/` 目錄中。

產物生成（Artifact Generation）：

- 檔案建立後，必須使用 PlantUML CLI 將所有 `.puml` 檔案轉換為 PNG 圖片。
- 課程指定指令如下：

```shell
java -jar plantuml.jar "./diagrams/*.puml"
```

- 所有 PNG 檔案必須與對應的 `.puml` 檔案儲存在同一個 `./diagrams/` 目錄中。
- 若 Windows PowerShell 對萬用字元或路徑的處理不同，必須使用等效 CLI 指令逐一轉換，
  並確認每個 `.puml` 都已實際產生對應 PNG；僅建立原始檔不算完成。

規劃階段（Planning Phase）：

- 在 `speckit.plan` 階段，必須將 Component Diagram、Class Diagram 和
  Sequence Diagram 作為主要設計藍圖，用來規劃系統架構、資料模型、模組及組件。

實作階段（Implementation Phase）：

- 在 `speckit.implement` 階段完成程式碼生成後，必須執行驗證步驟，
  確認最終程式碼與三種圖表一致，並保存驗證紀錄。
- 若實作與圖表不一致，必須依已確認需求修正並重新驗證；
  修改 `.puml` 後必須重新產生對應 PNG。
- 涉及使用者功能或操作流程的變更，必須先依原則 I 與另一組討論，
  不得以更新圖表代替需求確認。

理由：以設計圖連結規格、規劃與實作，落實課程指定的設計優先流程。

### IV. 搶答公平與資料正確性

- 搶答順位只能由後端決定，不得信任學生裝置時間作為順位裁定依據。
- 每組每題最多接受一次有效提交；多組同時提交或同組重複提交時，
  後端仍必須維持此限制與一致的順位結果。
- 老師結束搶答後，後端不得接受新的答案；提交有效性必須依後端活動狀態判定。
- 學生在搶答結束前不得取得其他組別的作答資訊；後端回應及同步資料皆須遵守此限制。
- Guided Notes 匯出必須保留題目與原始工作表內容，且不得寫死答案儲存格位置。

理由：由後端統一裁定狀態及提交，確保公平性、資訊隔離與檔案完整性。

### V. 系統簡潔與安全

- 系統只需在本機運作，不需要公開部署；不得將公開部署列為核心交付要求。
- 老師權限必須由後端驗證，不得僅依賴前端隱藏介面或客戶端傳入的角色資訊。
- 不得將密碼、金鑰或機敏資訊提交至 GitHub。
- 活動資料在後端執行期間必須保留；後端重啟後允許清空。
- 架構選擇必須優先採用容易理解、測試及維護的方案；增加複雜度時，
  必須在設計文件中說明與核心需求的關聯及必要性。

理由：以本機課堂使用為基準，維持必要權限保護及資料生命週期，控制維護成本。

### VI. 驗證與文件

- 必須執行 AI 自動測試及人工測試，兩者都必須留下實際執行紀錄。
- 必須驗證多組同時提交、重複提交、活動同步、權限隔離、檔案匯入匯出與異常處理。
- 必須保存規格文件、設計圖（包含 `.puml` 與 PNG）及測試紀錄。
- 測試紀錄必須記載執行方式、預期結果、實際結果及通過或失敗狀態；
  未執行或受阻的測試必須如實標示。
- 不得宣稱未實際執行的測試已經通過。

理由：以可核對的執行證據確認成果，避免以文件描述或 AI 宣稱代替驗證。

## 專案背景與範圍

ClassroomQuiz 是 2026 軟體工程期末專題，使用 OpenAI Codex 與 GitHub SpecKit
進行 AI Agent 開發，目標為建立一套本機運作的課堂線上搶答系統。

核心範圍為老師端、學生端、Guided Notes 匯入匯出、搶答順位與活動階段同步。
功能細節必須以老師指定需求及兩組確認的規格為準，本文件不授權加入未確認功能。
Guided Notes 匯入不代表允許新增題組匯入功能，兩者不得混淆。

## 開發流程與品質關卡

1. **Constitution**：建立或更新治理規則並接受人工審查；此階段僅處理 Constitution。
2. **Specify**：確認需求與驗收條件，完成三種 PlantUML 圖與全部對應 PNG，
   並由人工審查 AI 產出的規格及設計文件，才可進入規劃。
3. **Plan**：以已確認規格及三種圖表規劃架構、資料模型、模組及組件，
   檢查六項原則的遵循情形，並完成人工文件審查。
4. **Tasks**：依規格與規劃拆解可執行、可驗證的任務，涵蓋必要測試、
   圖表一致性驗證與文件保存，並完成人工文件審查。
5. **Implement**：依已確認任務實作，執行 AI 自動測試、人工測試及程式碼與圖表一致性驗證。
   差異或測試失敗必須修正並重新驗證；規格、設計圖、程式碼與 Demo 一致後才可視為完成。

各階段審查必須記錄結果及尚未解決的問題。涉及使用者功能或操作流程的變更，
必須先完成跨組討論，再更新相關規格、設計、任務與實作。

## Governance

- 本 Constitution 為專案開發的最高治理基準；規格、設計、任務、程式碼、測試及 Demo
  均必須遵循。任何不符合強制原則的成果，不得標示為完成。
- 修訂必須記錄原因、變更內容及受影響產物，經專案成員人工審查確認後生效；
  影響使用者功能或操作流程時，必須事先與另一組討論並保存結論。
- 修訂後必須檢查受影響的規格、設計圖、任務、程式碼、Demo 與測試紀錄，
  記錄必要的同步修正工作；Constitution 更新命令本身僅修改本文件。
- 版本採語意化版本 `MAJOR.MINOR.PATCH`：不相容的治理變更、原則移除或重新定義
  遞增 MAJOR；新增原則、章節或實質擴充規則遞增 MINOR；不改變含義的澄清或錯字修正
  遞增 PATCH。首次正式制定版本為 `1.0.0`。
- 每次修訂必須更新版本及最後修訂日期，保留首次批准日期，日期格式為 `YYYY-MM-DD`。
- 每個階段關卡及變更審查都必須核對本文件，特別確認核心範圍、跨組一致性、
  三種 PlantUML 圖及 PNG、後端公平性與權限、實際測試證據及人工文件審查。
